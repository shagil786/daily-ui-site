# Daily UI Site — Design Spec

**Date:** 2026-10-02
**Status:** Approved (design sections reviewed in chat)
**Path:** Architectural

## 1. Purpose & Intent

A portfolio site that renders a **fully random UI every day** — not just portfolio content in changing layouts, but entirely new UIs (games, widgets, art pieces, dashboards). Portfolio output is one possibility among many.

- **v1:** Daily generated UI + browsable archive.
- **Future:** agent attached in the frontend — user describes a desired UI and it renders; or the UI adapts to the user's mood. The v1 architecture must accommodate this without a rewrite.

**Success criteria:** visiting the site today shows a valid, interesting, non-broken UI generated by an LLM; it is different tomorrow; past days are browsable; nothing the agent emits can crash or compromise the page.

## 2. Approach Decision

Chosen: **Schema-first + SQLite (approach C)**.

- The Zod schema and typed component registry are the real architecture — they make "render anything the agent generates" safe.
- SQLite (`better-sqlite3`) stores generated days: no external service, one file to back up, trivial archive queries, and the model extends to user-generated/mood-based variants later.
- Rejected: file-backed (throwaway storage layer, weaker future fit), full Postgres (heavy for v1, external dependency).

**Stack:** Next.js (App Router, TypeScript, React) — single codebase for pages, API routes, and cron-triggered generation.

## 3. Architecture

```
Next.js app
├── app/
│   ├── page.tsx            → renders today's UI
│   ├── archive/page.tsx    → list of past days
│   ├── archive/[date]/     → renders a past day
│   ├── api/today           → validated JSON for today
│   ├── api/archive         → list of past days; /api/archive/[date]
│   └── api/generate        → trigger generation (secret-protected)
├── lib/
│   ├── schema.ts           → Zod: UiDocument = { version, date, title, theme, root }
│   ├── registry.tsx        → typed map: componentType → { propsSchema, Component }
│   ├── renderer.tsx        → recursive Node → React renderer with guards
│   ├── validate.ts         → document + per-node props validation walk
│   ├── llm/provider.ts     → interface generate(prompt) → string
│   │   ├── openai.ts
│   │   └── anthropic.ts
│   └── db.ts               → better-sqlite3: days table
└── scripts/generate.ts     → CLI: generate date ranges, validate, upsert
```

### Daily flow

1. Cron (self-hosted node-cron, or external scheduler) calls `POST /api/generate` with secret header.
2. Provider builds prompt → LLM returns JSON → JSON extraction → Zod validation.
3. On failure: one repair attempt ("here's the error, return corrected JSON"); still failing → reuse yesterday's document flagged `stale: true`.
4. Upsert into SQLite. `GET /api/today` (and direct server-side DB read in the page) serves it.

### Render flow

`page.tsx` loads today's doc → sets theme CSS variables (`--bg`, `--fg`, `--accent`) on `<html>` → renderer walks `root` recursively → each node looked up in registry → unknown type or invalid props → safe placeholder / default (never crash).

## 4. Schema & Component Registry

```ts
// lib/schema.ts — Zod
UiDocument = {
  version: 1,
  date: "YYYY-MM-DD",
  title: string,                       // document title + meta
  theme: { bg, fg, accent, font: "serif"|"sans"|"mono"|"display", dark: boolean },
  root: Node
}

Node = {
  id: string,
  componentType: string,               // must exist in registry
  props: Record<string, unknown>,      // validated per-component via propsSchema
  children?: Node[],                   // layout components only
}
```

- Registry entries: `{ propsSchema: ZodSchema, Component }`.
- Validation pipeline: document schema first, then per-node `propsSchema` walk. Any failure → regenerate or fallback.

### v1 component inventory (~25, "wide")

| Group | Components |
|---|---|
| Layout | Stack, Grid, SplitPane, Tabs, Timeline, Center, Section |
| Content | Hero, Text, Card, ImageGallery, LinkList/Socials, BeforeAfter, TerminalSim |
| Interactive | Counter, Todo, Poll, Clock, Clicker game, Marquee, CanvasNoise (animated), ProgressBar, Accordion |

### Safety rails

- **Hard limits in Zod:** depth ≤ 8, total nodes ≤ 300.
- **URLs:** images only `https` from an allowlist (or data-URIs with size cap); no arbitrary remote fetches.
- **No HTML injection:** text rendered as text (React escapes); no `dangerouslySetInnerHTML`, no `eval`, no callbacks in schema.
- **Unknown componentType / invalid props:** placeholder box in dev; silent swap for safe default in prod.
- **Error boundary per node** so one bad widget cannot white-screen the page.

## 5. Generation Pipeline

- **Prompt:** system prompt embeds the component inventory (auto-generated from the registry: names, prop schemas, limits), today's date, and a daily "directive" from a curated variety pool (retro terminal, brutalist poster, soft pastel, game-like, minimal portfolio, data-viz dashboard, …). Demands JSON only.
- **Structured output** where supported (OpenAI `response_format`, Anthropic tool-use); plain JSON extraction fallback otherwise.
- **Provider abstraction:** `LLM_PROVIDER=openai|anthropic` + `LLM_API_KEY`; `llm/provider.ts` interface so either works via config (provider to be chosen later).
- **Retry:** parse fail → 1 repair attempt → fallback to yesterday's doc with `stale: true` (UI shows a small "yesterday's" badge).
- **Storage:** `days(date PK, json, directive, stale, createdAt)` — regeneration overwrites.
- **Orchestration:** `scripts/generate.ts --from --to` for local/backfill; `POST /api/generate` (secret header) for cron. Same code path.

## 6. Frontend

- **Today page:** server component; direct DB read server-side (fewer hops than API self-call). Theme via CSS variables. Fixed corner badge: date + archive link.
- **Archive page:** server-rendered list — date, directive name, stale flag, text preview of `title` (thumbnails deferred to a later iteration). Click → `/archive/[date]` renders through the same renderer.
- **Error handling:** DB miss for today → attempt one server-side generation (using server-held credentials, never the client-facing secret); if that fails, serve the latest available doc with a "showing most recent" badge. Rate-limit on-demand generation to once per render attempt to prevent hammering the LLM.

## 7. Testing

- **Unit (Vitest):** schema validation (valid/invalid docs, depth/node limits), renderer node-walk, registry lookup + unknown-type fallback, LLM JSON extraction and retry logic with mocked provider.
- **E2E (Playwright):** smoke — today page renders a node tree; archive navigates to a past day.

## 8. Future Extensibility (designed in, not built)

- `UiDocument` can gain optional `audience` / `mood` fields without breaking v1.
- `POST /api/generate` accepts an optional `brief` param already present in the provider interface → user-described UIs later.
- Registry is the single place to add components for new agent capabilities.
- No schema or storage rewrite required for the future frontend-attached agent / mood-driven variants.

## 9. Configuration & Security

| Env var | Purpose |
|---|---|
| `LLM_PROVIDER` | `openai` \| `anthropic` |
| `LLM_API_KEY` | provider key (server only) |
| `GENERATE_SECRET` | shared secret for `POST /api/generate` |
| `DATABASE_PATH` | SQLite file path |

- No secrets in the client bundle; generation endpoint rejects requests without the secret so strangers cannot burn API credits.
- All external input (LLM output, future user briefs) treated as untrusted and validated against Zod before render.

## 10. Out of Scope for v1

- User accounts / auth
- On-demand user-described UI generation (interface allows it; no UI)
- Archive thumbnails
- Provider-specific features beyond structured output
- Deployment specifics (self-host vs Vercel) — SQLite favors self-hosting or a persistent disk; decide at implementation time
